# 设计说明（2026-10-19）

一页纸的架构与决策记录，用于面试前过一遍，也用于解释“哪些是上游、哪些是本次改动”。

## 定位与边界

- 上游：`langchain-ai/local-deep-researcher`（MIT），提供 LangGraph 研究图与基础节点。
- 本仓库在上面加了三层：**本地模型适配**、**可执行的失败语义**、**FastAPI + SQLite 报告服务**。
- 不做的事：没有工具调用（`use_tool_calling` 默认 False，上游结构化输出分支）、没有向量 RAG、自由网页搜索未验收。

## 运行链路

```text
浏览器 / curl
   ↓ POST /research
FastAPI（127.0.0.1:8765）
   ↓ 校验入参（Pydantic）
run_research(topic, loops, source_urls)
   ↓
LangGraph：generate_query → web_research → summarize_sources → reflect → 路由
   ↓ 调用模型
本地模型服务（127.0.0.1:1235，OpenAI 兼容）
   ↓
SQLite（reports 表）+ outputs/<id>.json + outputs/<id>.md
```

## 节点与状态

- `summary_state` 里关键字段：`research_loop_count`、`search_status`、`sources_gathered`、`running_summary`。
- `search_status` 三态：`success` / `empty` / `failed`。取值为非 success 时，`summarize_sources` 与 `reflect_on_summary` 直接跳过。
- `route_research`：`search_status` 非 success → 进 `finalize_summary`；否则 `loop < 预算` 才继续搜。

## 接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/health` | 应用存活（不探测模型） |
| GET | `/` | 研究工作台页面 |
| POST | `/research` | 触发一次研究，同步返回结果 |
| GET | `/reports` | 最近 30 条报告 |
| GET | `/reports/{id}` | 单条报告详情 |
| GET | `/reports/{id}/download` | 下载 Markdown 正文 |
| GET | `/reports/{id}/check` | 7 条规则的质量自检 |
| GET | `/reports/{id}/compare/{other}` | 两次运行的结构化对比 |

入参约束（Pydantic）：主题 3–300 字、轮次 1–3、来源最多 5 条。

## 三个决策

1. **只支持指定 HTTPS 来源。**
   本地小模型做开放式搜索时结果不稳定、经常超出预算；先把输入可控和引用可追溯做扎实，再横向扩源。

2. **失败与空结果分开。**
   原先超时和“搜到 0 条”走同一条路，模型会拿空来源继续编。拆成三态后，失败或空结果直接进总结节点。

3. **预算判断用严格小于。**
   路由原先用 `<=`，计数器到上限时又被放行一次，导致“上限 1 轮”实际跑 2 轮。改成 `<`，并用参数化用例断言“实际搜索次数 = 预算”。

## 第四层（本仓库新增）：来源策略

`local_app/policy.py` 在进入研究图之前先过滤 `source_urls`，规则按顺序执行，被丢弃的链接都带原因：

| 规则 | 默认值 | 为什么 |
| --- | --- | --- |
| 只收 http / https | — | 挡掉 `file://`、`ftp://` |
| 同域名上限 | 2 条 | 防止单一站点主导引用，报告看起来引了 5 条其实是一家在说 |
| 判重 | 去 fragment、去尾斜杠、统一 host 大小写 | 同一页重复喂给模型是浪费上下文 |
| 黑名单 | 可配 | 排除已知不可靠站点或内网地址 |
| 白名单 | 可配（非空时生效） | 限定可信来源范围 |
| 总数上限 | 5 条 | 与 Pydantic 的 `max_length=5` 对齐 |

执行结果写进每条报告：`sources_kept` 与 `sources_dropped[{url, reason}]`。若全部被过滤，直接返回 failed 且**不调用模型**——省一次无意义的模型调用，也避免“没有来源还硬总结”。

## 质量保障

- **66 项 pytest**：预算、异常三态、API、配置独立性、质量自检规则、来源策略、报告对比。
- **11 项接口集成测试**（`scripts/system_test.py`）：对真实端口打 200 / 404 / 422，产出 `outputs/checks/system-test-*.json`。
- **7 条规则自检**（`local_app/quality.py`）：状态完成、Summary、Sources、引用、长度、循环未超预算、error 为空。
- 这是**规则层**的检查，不是报告事实准确性的评测。

## 第五层（本仓库新增）：报告对比

`local_app/compare.py` 比较同一主题的两次运行，输出：

- **引用增删**：新增哪些 URL、丢掉了哪些、共有哪些；
- **规则通过项变化**：哪条检查从失败变通过（fixed）、哪条从通过变失败（regressed）；
- **数值变化**：字符数、耗时、轮数；
- **结论**：`improved` / `degraded` / `more_citations` / `fewer_citations` / `length_changed` / `unchanged`。

入口有两个：`GET /reports/{a}/compare/{b}` 和 `scripts/compare_reports.py`（可 `--write` 留档）。

用处：改了一处逻辑后，用同一主题再跑一次，**用差异说话，而不是凭感觉说“好像变好了”**。它只做结构化对比，不判断哪份报告在事实上更准确。

## 已知短板（面试可主动说）

- 没有工具调用闭环，模型不能自主选择业务工具。
- 没有 RAG / 向量库，来源是“给定 URL”而非检索。
- 报告质量只有规则自检，没有人工标注的评测集。
- 同步接口，长时间研究会把请求挂住（当前单次约 10–90 秒）。
